If you run AI coding agents like Claude Code, OpenCode, Cline, or Aider, your API bill has a dirty secret. The same tokens get processed over and over, and you pay full price every single time.

A single agentic session resends its entire conversation history on every tool call. By turn 20, a request might carry 200,000 prompt tokens, and 95% of them are identical to the previous request. That is not a bug. It is how the chat completions API works. But paying full input price for tokens the model has already seen is money burned.

Prompt caching fixes this. And if you are not using it, you are overpaying by a lot.

## What prompt caching actually does

When a request arrives, the provider checks whether the beginning of the prompt, the prefix, matches a recently processed one. If it does, that portion is served from a cache instead of being recomputed. Cached tokens are billed at a cache read rate, which is dramatically cheaper than the normal input rate.

The numbers vary by model, but they are consistent in direction:

- GLM-5.2: cache reads cost about 5x less than input tokens
- DeepSeek V4 Flash: about 5x less
- Claude Opus 4.6: about 10x less
- GLM-5.3: about 5x less

For an agent that resends a growing prefix on every turn, this is the single biggest cost lever available. Nothing else comes close.

## Real numbers from live traffic

We enabled cached token billing on Ruvicode this week. Here is what an actual agentic session looks like on our gateway, using GLM-5.2.

A typical request mid-session:

```
prompt_tokens:      299,541
```

The same request without caching would bill all 299,541 tokens at the full input rate. With 99.7% served from cache, the input portion of the bill drops by roughly 74%. On a long session with hundreds of turns, the total savings compound into serious money.

The interesting part: the person running this session did nothing special. No flags, no parameters, no code changes. Caching matched the repeated prefix automatically.

## Which workloads benefit most

Prompt caching pays off whenever the same prefix repeats.

- **Coding agents** are the best case. Tool loops resend the whole conversation on every call, so cache hit rates of 95%+ are normal after the first few turns.
- **Chat with long history** benefits the same way. Every follow-up message carries the entire prior conversation.
- **Stable system prompts** over 1,024 tokens get partial benefit even in one-shot workloads, if the same system prompt is reused across requests.
- **One-shot, unique prompts** get nothing. If every request is completely different, there is no prefix to reuse and every token bills at the input rate. That is fair, and it is how it should work.
